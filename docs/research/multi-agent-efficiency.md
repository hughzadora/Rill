## Findings

- Native collaboration provides `list_agents`, `send_message`, `followup_task`, `wait_agent`, and `interrupt_agent`. `followup_task` assigns more work to an existing non-root agent and starts or resumes its turn; interruption preserves context. Use one fresh worker when a workflow begins, then query the native roster and follow up that worker for same-domain increments with only changed scope/evidence. Spawn another worker only for independent work that can run in parallel. This follows the [official Multi-agent guide](https://developers.openai.com/api/docs/guides/responses-multi-agent), which recommends bounded independent work and one agent for short or ordered work; it also avoids rereading unchanged sources. Cross-session worker reattachment is not established by this guide.
- Codex’s [configuration reference](https://learn.chatgpt.com/docs/config-file/config-reference) defines `agents.max_concurrent_threads_per_session` as the cap on spawned-agent threads, excluding the primary. Rill’s current `.codex/config.toml` is set to 2. That permits up to two workers alongside the coordinator; retain it for two independent tracks, not serial phases. Source-dependent steps that build on prior results should follow up the same worker.
- Rill currently declares coordinator default Sol low and subagent default Luna high in `.codex/config.toml`. Role files explicitly set `explorer` and `worker` to Luna high, `reviewer` to Sol low, and `risk_reviewer` to Sol medium (`.codex/agents/*.toml`). Codex first resolves spawn selection, then the corresponding `[agents]` default, then the parent value; a named role file's `model` or `model_reasoning_effort` takes precedence over those resolved values, per the official [subagents guide](https://learn.chatgpt.com/docs/agent-configuration/subagents). The app-server schema distinguishes thread configuration from turn-level facts: `ThreadStartedNotification.json` says the thread `model` field is not per-turn telemetry, while `TurnStartedNotification.json` records the resolved subagent model/effort at creation. Use observed turn/agent metadata when reporting what ran.
- The local [`ThreadTokenUsageUpdatedNotification.json`](/home/hugh/Projects/.artifacts/Rill/native-feasibility-2026-11-18/schema/v2/ThreadTokenUsageUpdatedNotification.json) reports per-thread, per-turn usage: last and total token breakdowns, input/cached/cache-write input, output, reasoning output, and optional context-window size. It has no currency-cost field and does not attribute tokens to a particular file read, prompt clause, or task outcome. The official [deployment checklist](https://developers.openai.com/api/docs/guides/deployment-checklist) recommends comparing completed-task quality, evidence, total tokens, latency, and cost against direct-call workflows. Native token counts alone cannot establish dollar cost or that delegation improved quality; measure outcomes and latency for a comparable batch, and obtain monetary cost from an authoritative billing source if needed.

## Minimal recommendation

No model, effort, or thread-cap change. Keep the existing Sol/Luna defaults. The standard should say: _new workflow → one suitable worker; same workflow increment → `list_agents` then `followup_task` with the delta; independent source tracks → parallel workers up to the native cap_. No forced-first-dispatch hook or custom scheduler is needed.

## Limits and source identity

The public docs are rolling and do not guarantee every behavior for build 0.170; the local schema snapshot is the version-specific native boundary used here. Per-thread token collection/aggregation across all child threads was not exercised in this research, nor was it established that closed workers can be resumed across sessions. Config declarations do not prove the active model; preserve actual resolved turn metadata with workflow evidence.
