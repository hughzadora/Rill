# Lauren Tan's product and agent engineering practices

Tan's most transferable idea for Rill is to relieve the owner of engineering supervision by giving agents a reliable way to observe product behavior. The owner supplies product judgment. The repository supplies good examples, enforceable boundaries, and a short path from a change to evidence. This is an interpretation of her published work, with adoption recommendations for Rill. [All Code Is Slop, 1:31–3:15 and 9:40–13:30](https://www.youtube.com/watch?v=O_zcc6Xl12g&t=91s)

## Product judgment

### Make the experience concrete while changes are cheap

In her 2015 Experience First essay, Tan defines design as how something works across the whole experience, including the balance between form and function. Her 2019 Netflix talk abstract applies that scope to the studio workflow from pitch to play, spanning content teams and production partners. The pstack experience-first principle extends the same consideration to API consumers and future maintainers. For Rill, one-command setup and a handoff that a new maintainer can actually repeat are part of the product experience. The continuity across these sources is an interpretation. [Experience First essay](https://www.no.lol/2015-04-10-the-importance-of-being-experience-first/) · [Netflix talk abstract](https://www.no.lol/speaking/2019/netflix/) · [pstack Experience First](https://github.com/cursor/plugins/blob/9e278fe4d4ecd8bfe98b1b79bf4be662efb338cc/pstack/skills/principle-experience-first/SKILL.md)

The prototype playbook starts with a decision to resolve. It uses scratch code, compares meaningful alternatives when a decision is open, and observes the relevant surface. For UI, that means actually driving the interactions. The deliverable is the chosen direction, evidence, and a disposable artifact. For production work, the architecture skill examines affected systems and sketches types, signatures, and module boundaries before implementation. Its selection criteria include one owner per piece of state and fewer details for callers to learn. [Prototype playbook](https://github.com/cursor/plugins/blob/9e278fe4d4ecd8bfe98b1b79bf4be662efb338cc/pstack/skills/poteto-mode/playbooks/prototype.md) · [Architect skill](https://github.com/cursor/plugins/blob/9e278fe4d4ecd8bfe98b1b79bf4be662efb338cc/pstack/skills/architect/SKILL.md)

The pstack README says that code makes the best specification and omits a default planning skill. Its feature playbook still begins with design and ends with runtime verification. Its multi-phase playbook supports durable plans when the work needs them. The distinction matters for Rill. An HTML prototype can settle what users should see and do. A schema can settle what a boundary accepts. A short written record can preserve why an option was chosen or which compatibility promise to keep. Each artifact answers a different question. [pstack README](https://github.com/cursor/plugins/blob/9e278fe4d4ecd8bfe98b1b79bf4be662efb338cc/pstack/README.md#why-are-there-no-planning-skills) · [Feature playbook](https://github.com/cursor/plugins/blob/9e278fe4d4ecd8bfe98b1b79bf4be662efb338cc/pstack/skills/poteto-mode/playbooks/feature.md)

Tan's 2020 essay challenges the idea that a clean slate and fashionable best practices can produce permanently ideal software. She asks what problem a pattern solves, what opportunity cost it brings, and which tradeoffs the team accepts. This qualifies the appeal of a deep template foundation. A pattern belongs in Rill when it helps a real project take the next step or prevents a failure the template can demonstrate. [This Time Is Different](https://www.no.lol/2020-05-11-this-time-is-different/)

### Preserve the owner's intent and remove routine mediation

In the Pocock interview, Tan describes intent transfer as a bottleneck even when models are capable. Domain expertise helps an owner articulate the outcome. She connects grilling to finding language that the owner recognizes and the agent can reuse. The pstack reframe skill makes that concrete by starting with the operator's words and files, distinguishing plausible interpretations, and grounding relevant terms in real examples. Rill can use the same method to return an ordinary-language playback of the need, then ask about the product choice that changes the result. [Pocock interview, 6:51–10:09](https://www.youtube.com/watch?v=MN9dGgmLyso&t=411s) · [Reframe skill](https://github.com/cursor/plugins/blob/9e278fe4d4ecd8bfe98b1b79bf4be662efb338cc/pstack/skills/reframe/SKILL.md)

Tan also distinguishes the **inner loop**, in which agents build against a snapshot of intent, from the **outer loop**, in which bug reports and new facts arrive. In her work the outer loop can feed reports to agents that reproduce issues using existing verification tools. The small-team version for Rill can start with a user report or an issue, a reproduction, and one decision about what to change. An owner should spend attention on what the product should do. The agent can gather diagnostics and rerun the affected journey. [Pocock interview, 33:34–38:48](https://www.youtube.com/watch?v=MN9dGgmLyso&t=2014s)

## Engineering practices

### Let structure carry repeated decisions

Tan's inverted pyramid places codebase design first, then static checks, runtime and formal verification, prose, and human review. The codebase serves as an agent's working memory because agents copy examples they encounter. Her talk describes Cursor agents using timers to bridge imperative and declarative code. Local explanations made those workarounds look intentional while the aggregate timer churn hurt responsiveness. In Grok Bot's Electron framework Dune, the team placed main and renderer code in explicit directories and enforced import boundaries. It also confines `useEffect` to selected framework APIs. These decisions address that application's observed failures. [All Code Is Slop, 2:07–9:40](https://www.youtube.com/watch?v=O_zcc6Xl12g&t=127s)

Her earlier type-systems talk makes the boundary precise. A return type can guarantee that a function returns an element, while still allowing the wrong element. Types reduce the valid state space and make interfaces explicit. Runtime parsing checks external values, and behavior tests establish which valid result the caller actually needs. A rejected PR input is a schema concern in Rill. An installable tarball that resolves its advertised entry point requires a consumer exercise. [Learning to Love Type Systems](https://www.infoq.com/presentations/type-system-typescript-flow-graphql/) · [Rill release rehearsal](acceptance.md#local-release-rehearsal)

The published `/correct` skill gives a repeatable adoption test. Group recurring mistakes, fix each at the highest practical level, and demonstrate that the resulting check catches a real past bad case. Prefer a single supported API or a type that excludes the invalid state. Use a diagnostic when the language can still express the mistake and a behavior test when the failure depends on execution. Preserve prose for rationale and judgment. In Rill, the release rehearsal already illustrates the method: a genuine Changesets record failed, the document gate learned the native artifact boundary, and the generated version and changelog then passed qualification. [Correct skill](https://github.com/cursor/plugins/blob/9e278fe4d4ecd8bfe98b1b79bf4be662efb338cc/pstack/skills/correct/SKILL.md) · [Rill release rehearsal](acceptance.md#local-release-rehearsal)

React Compiler provides an earlier example of a team moving work into tooling. Tan and her coauthors describe using compiler analysis to optimize idiomatic React and surface Rules of React diagnostics through linting. They offer incremental adoption and recommend end-to-end testing because changes to memoization can expose unexpected behavior. The lesson for Rill is to put repeated work in a safe default and retain a way to observe compatibility as it changes. This is a team project and a joint publication. [React Compiler v1.0 announcement](https://react.dev/blog/2025/10/07/react-compiler-1)

### Verify on the user's surface and preserve the evidence

In the talk and the pstack verification skill, a feature map names the important paths from the user's point of view. A verifier can start the actual app in isolation, confirm it is ready, drive it through existing tools, inspect the side effects, and preserve a screenshot, recording, transcript, or response. The skill calls for one real drive of a mapped feature before handing over the recipe. pstack's shipping playbook then asks a separate agent to exercise the candidate relative to its parent. The author's iteration loop and the independent shipping check serve distinct purposes. [All Code Is Slop, 9:40–13:30](https://www.youtube.com/watch?v=O_zcc6Xl12g&t=580s) · [Verification skill](https://github.com/cursor/plugins/blob/9e278fe4d4ecd8bfe98b1b79bf4be662efb338cc/pstack/skills/create-verification-skill/SKILL.md) · [Shipping playbook](https://github.com/cursor/plugins/blob/9e278fe4d4ecd8bfe98b1b79bf4be662efb338cc/pstack/skills/poteto-mode/playbooks/shipping.md)

Tan reports more than 3,000 individual production PRs and about 11,000 across the team in a month, with the revert rate settling around 0.5%. These are self-reported figures from one organization. A revert count misses defects fixed forward, and PR size and content affect throughput comparisons. Tan also reports startup, typing, and chat-navigation improvements. Rill can measure whether agents preserve user-facing behavior and whether owners spend less time shepherding verification. [All Code Is Slop, 13:32–17:31](https://www.youtube.com/watch?v=O_zcc6Xl12g&t=812s)

### Adopt autonomy in increments

Tan describes starting with a reliable edit-and-check loop, then adding coordination and release-triggered checks. On Grok Bot, she discusses automated release fuzzing and repairs backed by established project constraints. Her Noodle project exposes auto, supervised, and manual modes, which shows that the autonomy level can be a product control. The useful increment for Rill is an agent that can present a verified change for the owner's decision. Self-merge and unattended release require a separate governance decision and separately controlled permissions. [All Code Is Slop, 15:11](https://www.youtube.com/watch?v=O_zcc6Xl12g&t=911s) · [Noodle](https://poteto.github.io/noodle/)

## Implications for Rill

| Area                 | Existing position                                                                                                                       | Proposal to test                                                                                                                                                                                                  |
| -------------------- | --------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Product discovery    | Brainstorming and owner review of HTML for significant UX changes                                                                       | Define the decision before prototyping. When the answer is open, make two small interactive variants and let the owner try the same task in each. Record the chosen behavior and reason.                          |
| Executable contracts | Zod and TypeScript at changed external boundaries, with checks through mise and Turbo                                                   | For each recurring mistake, first check whether a simpler module boundary or single supported API would remove it. Keep checks that catch a concrete failure and tell the author how to resolve it.               |
| Acceptance           | Local qualification and a real npm tarball consumer exercise                                                                            | On the next actual product, give the agent a concise list of user journeys and the existing commands to start and verify them. Capture one success and one meaningful failure through the real product interface. |
| Independent review   | Owner retains merge and release authority. The remote independent gate still needs provisioned identities and a trusted check producer. | Use a fresh verifier for risky changes. Have it report the revision exercised, actions performed, observations, and remaining uncertainty. The owner judges product fit and controls the merge.                   |
| Scale and release    | Fast local feedback, stronger release qualification, and verified local rehearsal                                                       | Start with one useful journey and a repeatable local check. Add parallel verification or formal modeling when distinct failure modes justify the cost.                                                            |

These proposals apply the prototype, correction, verification, and shipping practices to the decisions already recorded in Rill. ### A small evaluation worth running first

Use a disposable CLI or UI project based on the current template. Pick a natural-language change that touches one established behavior and one error case. Run the same request twice in fresh workspaces with the same agent settings. One workspace uses the current template. The other adds a short journey map and uses the same existing runtime tools. A fresh reviewer receives the artifacts without variant labels and reruns the user path. Record whether the behavior is correct, whether the evidence can be reproduced without the original agent, how many owner interventions were needed, and the local time cost. Keep this as a single pilot before turning findings into template policy. The comparison isolates the value of the journey map. Further runs are needed to establish reliability across tasks. [pstack evaluation playbook](https://github.com/cursor/plugins/blob/9e278fe4d4ecd8bfe98b1b79bf4be662efb338cc/pstack/skills/poteto-mode/playbooks/eval.md)
