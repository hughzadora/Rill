# Rill behavioral design

## Direction

Rill owns the owner's shared development standard, explicit project enrollment, task continuity, evidence records, and verified native integration. Codex remains responsible for sessions, models, permissions, approvals, delegation and scheduling. GitHub remains authoritative for approved decisions and task execution; local recovery material protects work not yet synchronized. Installed Matt Pocock skills supply engineering methods.

The owner-confirmed visual review is [DESIGN.html](DESIGN.html), a dated view associated with [issue #17](https://github.com/hughzadora/Rill/issues/17). It covers the prior design only. The complete decision source is #17; current delivery evidence and open gates remain in [issue #18](https://github.com/hughzadora/Rill/issues/18). This proposal is for the overall-design checkpoint and is neither technical approval nor implementation evidence.

## Confirmed behavior

### Enter, resume and leave a project

An owner explicitly enrolls a Git checkout. Enrollment resolves the GitHub repository and authorized publisher, preserves effective project tools and configuration, and enables the native project entry. The owner binds a GitHub issue through task synchronization. Conflicting repository or publisher identity is surfaced for reconciliation. Installation and trust are host actions; enrollment alone does not grant trust.

At supported startup and resume events, Rill identifies the enrolled checkout and bound issue, supplies shared preferences and task context, and checks actual Git state, task snapshot, pending records and available native history. It reports reconciled, pending, missing and unknown information, then continues only authorized work whose requirements are available. History-page coverage shows what was read, not that every meaning was interpreted.

Task facts are durably added to a local outbox before publication. When online, Rill checks the authoritative GitHub task, publishes the pending fact and reads it back. The fact remains pending until readback confirms publication. Scope conflicts are surfaced. Offline work may continue within prior authorization and known requirements; delivery remains unconfirmed until synchronization succeeds.

Leaving requires pending facts to be published and read back. Rill disables the project entry and retains recovery cache, publisher authority and shared personal policy. Native configuration reload and actual cessation of hook invocation are separate host behaviors.

### Diagnose, repair and complete

A failure and expected behavior are recorded against the current candidate. Checks retain command, output and exit status; diagnosis links evidence to the failure; interpretation records the reason and proposed repair. Two consecutive failed repair rounds require fresh discriminating evidence. Repeated diagnosis without new evidence stops. Successful checks bind to the candidate and do not erase prior failures.

Acceptance compares current content with approved scope, actual full-spec evidence, independent review and owner decision. A mismatch or later-discovered requirement invalidates affected acceptance while retaining the earlier pass in history. Local audit cannot create GitHub authorization, merge protection or human acceptance.

### Human checkpoints and delivery

Use native input for consequential decisions that facts cannot establish, and native approvals for execution approval. The owner checkpoints from #16 cover requirements and consequential trade-offs, prototype and overall design review, user trial and final acceptance. Routine authorized work proceeds without asking again for known decisions.

The approved sequence remains requirements, quick prototype, HTML design, implementation, integration and user testing, cleanup, second verification plus human check, and one batch PR. Small tasks may combine stages while preserving their completion criteria. Scope reduction requires an owner decision.

### Implementation versus acceptance

At inspected revision `5ca5ab1`, the working tree also contains uncommitted recovery changes: startup refresh, explicit persisted recovery gaps, and allowing independent diagnostics while guarding supported dependent edits. These follow the intended flow above; their remaining negative-case checks and combined native execution are unverified. The existing manual/automatic compaction observations and repair-guard probe recorded in #18 concern their actual earlier versions and paths. The HTML view, this behavior description and content hashes are not evidence that this working tree has passed those scenarios.

## Proposed end-to-end design: one standard, configured once

### Goal and current feasibility evidence

The approved product direction is one centrally maintained, SemVer-versioned development standard for multiple explicitly enrolled projects. After a one-time user setup and one explicit enrollment per project, future development sessions should load the applicable rules and execute the configured pipeline without per-task model, agent or stage prompts. Pure questions and simple requests requiring no project-source work may be answered directly. For source work, the Sol coordinator first checks for a suitable native worker binding on the same workflow/code domain and continues it; it creates one fresh-context Luna worker/explorer only when no suitable binding exists or the work is independent. The coordinator integrates evidence and configured Sol reviewers independently review the completed batch. The current Sol low setting is preserved. No automatic Astra selection or effort increase is authorized.

The 2026-11-18 native baseline is bounded evidence, not a candidate certification:

- One clean app-server session completed an ordinary source question using `gpt-6.1-sol` at low effort. Its mode was `explicitRequestOnly`; the completed history contained 7 items (4 direct command executions), with zero exact collaboration or subagent activity items.
- The only reported instruction source was this project's `AGENTS.md`. The probe recorded `existsSync=false` for `/home/hugh/.codex/AGENTS.md`; that does not distinguish a missing file from a broken link. Full instruction-file hashes and contemporaneous worktree/candidate identity were not captured.
- The probe concluded that project enrollment does not install shared user-level policy. Native role files and a concurrency cap of two configure availability/defaults; they did not demonstrate automatic dispatch.
- Installed native package `0.1.2` and source candidate `0.1.3` were distinct. The observation is not bound to a candidate and does not certify either version. A separate Sol low probe review completed, but also does not establish candidate acceptance.
- The server reported ten ignored unrecognized settings, with three `trusted_content_hash` settings named and seven collapsed. Two plugin icon path warnings were also reported. These messages do not establish hook behavior or broader Rill failures.

The reviewed summary preserves the original summary and corrects its broad regex interpretation of agent messages as collaboration. Current hashes identify reviewed files, not contemporaneous execution receipts. Do not extend these observations beyond the stated session and fields, or infer that native automatic dispatch is impossible from this baseline.

### One-time setup and project contract

User setup installs a short native user-level router, configured role/model defaults, and one compatible native Rill runtime. Immutable Rill standard artifacts are resolved by exact project SemVer and digest through that runtime's compatibility map; the native plugin/runtime version is global and is not isolated per project. Setup verifies which instruction sources were loaded, active coordinator model/effort, configured roles, native tool availability and runtime version. The router resolves project context and current task from the host and authoritative GitHub record, then routes source work through the fixed pipeline. The user-level source is maintained and versioned by Rill; projects do not receive copies of the shared method or workflow text.

Project enrollment happens once for an explicitly selected repository. It verifies user setup and actual native configuration layers, resolves the exact standard pin, digest and supported tools, then records only project facts: repository identity, exact SemVer and artifact digest, actual tool bindings, explicit exceptions and project entry/task facts. It preserves effective native configuration, structures, local changes and symlinks. Missing user setup, unsupported standard, unknown tool binding or mismatched version leaves enrollment incomplete and visible; it does not ask the owner to repeat decisions already recorded. Existing schema-1 enrollment requires an explicit migration plan; it is never silently assigned the latest release.

An enrolled project contributes its product requirements, architecture, design, glossary, tools and exceptions. The shared standard contributes personal preferences, stage/checkpoint policy, CI and repair rules, and native adapters. Agents resolve the shared standard with project facts without copying shared process templates into project product documents.

### Fixed pipeline and dispatch behavior

Every new task/session resolves approved scope, authoritative issue, actual Git/worktree state, outstanding evidence and the next authorized work. It continues from the authoritative task and recovery record rather than restarting stages or asking again for recorded decisions. Native Goal creation is available only on explicit user request and is not a per-task prerequisite; routine continuity must not create or rebuild a Goal.

For source work, the native Sol coordinator first checks for a suitable worker binding on the stable workflow/code domain: continue a running thread or follow up its idle, interrupted or completed thread. A missing roster entry alone is not proof of unavailability. Create one bounded Luna context with task, owned scope, source references, required checks and completion condition only when no suitable binding exists, or the work is independent or needs a specialty; record why. Independent source tracks may run in parallel up to the configured cap of two; dependent increments continue with the same worker. The worker returns changes or findings plus exact evidence. The coordinator integrates them and avoids repeating the same investigation. A configured Sol reviewer independently reviews the completed batch and current evidence. Coordinator and review role/model defaults are resolved from actual host state and recorded, not assumed from configuration text. Missing explicit configuration keys alone do not prove an effective-default mismatch. Model unavailability or overrides are exposed; there is no silent substitution or automatic effort escalation.

The pipeline applies #16's requirements, prototype, overall HTML design, implementation, integration/user testing, cleanup, final verification/human check and batch PR stages according to task scope and risk. Matt Pocock methods guide the applicable work. Owner checkpoints remain human decisions. A focused investigation, read-only code fact-finding task or small change still uses the configured worker path when available, but does not claim irrelevant prototype, UI or CI stages were executed. Pure no-source questions remain direct. This dispatch default is instruction and task evidence, not a new hook that blocks the first source tool call. If native worker availability or a receipt is unknown, report that limitation and continue other already-authorized work; do not hold unrelated or non-core fixes behind dispatch evidence. Existing scope, repair, approval and final acceptance requirements still apply. Check the project command composition without repeatedly running full suites; commit hooks run lint only, development checks follow behavioral risk, and local full-spec CI runs once on the final batch candidate before independent review, owner acceptance and the single PR.

### Native controls, receipts and limits

The design is native-first: user/project instruction and role configuration establish defaults; actual native delegation performs worker/reviewer work; hooks guard only existing supported task/safety boundaries; MCP exposes structured project/task/evidence operations and results. When the native host exposes them, record delegation receipts on the existing task/MCP evidence path with parent and child thread IDs, resolved model/role, bounded scope, candidate, returned result and command/evidence references. The existing task checkpoint carries a stable workflow ID, source checkpoint revision, verified source hashes and next action. These records aid continuation but do not prove a native thread is still available; check the native binding before reuse. Delivery evidence can consume available receipts and current candidate identity. A receipt is evidence of declared and observed invocation fields, not semantic correctness by itself. Missing or unsupported receipt events remain visible as unknown; they do not create a new first-dispatch gate.

Do not add hooks solely to force first dispatch or stop independent authorized work while waiting for worker evidence. Native automatic-delegation features that silently raise effort are not the default because that change is unauthorized. Existing hook boundaries remain limited to verified native events and actual supported controls. If a required acceptance behavior cannot be observed through supported routes, report the exact gap, evidence and operating trade-off for the design checkpoint. Do not treat added instructions or configured role files as proof that a worker ran.

No Stop/continuation mechanism or pre-tool dispatch guard is part of this proposal. If later acceptance evidence shows a concrete gap, document the observed behavior and native-supported alternatives for a separate owner design decision; do not make such a mechanism a prerequisite for unrelated authorized work.

No custom scheduler, workflow DSL, session service, parallel task database or approval UI is proposed. Codex retains session lifecycle, actual dispatch, permissions, approvals and scheduling. Rill adds no native adapter without an evidenced gap and an actual consumer.

### Versioned standard and compatibility

Rill maintains one source for personal preferences, development stages, human checkpoints, CI timing, repair limits and their native adapters. Stable rule IDs connect human-readable policy to deterministic guards. Matt Pocock methods stay in their installed skills and are not copied into Rill.

A release manifest identifies exact SemVer, immutable artifact digest and Git revision, supported project schema, rule IDs, policy entry, runtime compatibility, native hook/MCP definitions and required tool capabilities. Use the existing native package/marketplace path, not a second package manager. A digest detects changed bytes but does not prove publisher provenance or trust. A release is immutable; SemVer does not replace behavioral verification or authorize an upgrade.

The compatibility surface includes project schema, stable rule/exception IDs, CLI/MCP contracts, managed-adapter contract and observable guard behavior. Use SemVer 2.0.0: after 1.0, breaking changes increment major, compatible additions minor and compatible fixes patch; prereleases are explicit and build metadata does not affect precedence. During 0.x, a new minor is proposed for breaking public changes and explicit migration is still required. Standard artifacts are immutable and pinned per project; the installed native runtime is global. Its compatibility map declares which artifact versions it can resolve and execute. Two project pins are supported only when the resolver and actual MCP/hook behavior demonstrate both; unsupported pins block dependent activation. Before changing the shared runtime, preflight every enrolled project's exact pin and preserve the old runtime/config for recovery. This is an implementation/pilot validation gate, not a separate native-install selector investigation prerequisite; do not claim multi-version execution until observed.

Installed `0.1.2` is legacy, not a certified version of the proposed format. `0.1.3` is source candidate distinct from that install. `0.2.0-rc.1` is a proposed first new-format candidate only; no version is published, installed or accepted by this design.

### Project tools and exceptions

Migrate explicitly to schema 2 with repository identity, exact standard version/digest, capability-to-command bindings and explicit exceptions. Credentials and absolute machine paths stay outside tracked declarations. Bind capabilities to actual executable argument arrays and repository-relative working directories; record discovered tool versions. Never evaluate declarations as shell. Validate actual Just/package/hook graphs where supported. Record inapplicable checks and unknown semantics honestly rather than inventing passing commands. Keep existing Just, Husky, Biome, TypeScript and project tools; replacing them is a separate decision.

Each exception names a stable rule ID, reason, bounded replacement or inapplicability, owner decision source and review trigger/version. Exceptions do not grant external permissions. Major upgrades, removed rules or exception-contract changes require reconciliation; wildcard exemptions and silently ignored unknown IDs are invalid. A small managed adapter may connect an existing lint recipe to a commit hook or expose the batch check entry. Record its generated bytes and owning release. Preserve scripts, hook chains, shebangs, modes and unrelated content. Conflicting or unrecognized integration blocks the plan; do not replace an entire Justfile, package manifest, `AGENTS.md` or hooks directory.

### Current implementation gap and module contracts

The implementation-gap inventory is a historical source snapshot (`5ca5ab1`); current control source is `3737ab3`, and #18 remains authoritative for current implementation and recovery state. At the historical snapshot, project enrollment validated schema 1 with repository identity and enabled a native plugin key; `tools/task-context.ts` embedded that v1 validator. There was no standard release manifest/resolver, schema-2 exact project pin, rule/tool/exception contract, cross-project support check, project inventory, distribution plan/apply/verify/rollback interface or multi-project integration test. `tools/native-config.ts` edited the project enabled flag through native `config/value/write`; it did not select a plugin version. The intended design does not require per-project native plugin installation: project pins identify immutable standard artifacts resolved by the compatible shared runtime. That runtime must map and execute every supported pin; unsupported artifacts block dependent project activation, and any shared-runtime upgrade preflights every enrolled pin. Verify two pins through resolver/MCP/hook behavior in implementation and the pilot; until then, make no claim that multiversion execution works. `tools/install-personal-policy.ts` supported explicit migration of a broken user `AGENTS.md` link and retained a recovery descriptor, but its managed-block replacement was not bound to a prior release or drift baseline. `.codex-plugin/plugin.json`, hooks and `.mcp.json` declared the current plugin and entry points but had no per-project standard resolver. This proposal does not authorize implementation before the overall-design checkpoint.

Keep interfaces small and let the existing Just/Node tools compose them; no workflow engine, scheduler, new project registry or copied project documentation is introduced.

### Version resolution, task evidence and recovery

For each supported project operation, resolve the enrolled root and pin, verify the artifact digest and runtime support, then expose effective version and exception/tool-binding digests in hook context and MCP results. The shared router resolves this release rather than embedding all releases in user instructions. Missing or unsupported versions stop dependent activation while permitting independent diagnosis; never fall back silently to latest or another worktree's declaration.

Recovery checkpoints, command/delegation receipts and delivery evidence bind standard artifact, effective exceptions and tool bindings, runtime, task and Git candidate identity. Upgrade or rollback preserves old records as history and rechecks affected acceptance against the effective version; previous acceptance cannot certify changed policy or wiring. Existing task sync/outbox remains the record path. Unknown compatibility or coverage stays unknown.

### Multi-project rollout, upgrade and rollback

The local operation contract is `inventory -> plan -> apply -> verify -> report`. Native registered-project output is one discovery input alongside explicit roots; expand real Git worktrees and report coverage. Trust paths are hints, not enrollment. Do not inspect private Codex databases or create a parallel registry. Classify each root as enrolled, legacy, disabled, unenrolled, missing/inaccessible, non-Git or unsupported; resolve canonical root, repository, Git common directory, branch/revision and status. Deduplicate aliases while retaining distinct worktree configuration. Unenrolled projects are discovery candidates, never write targets without a named owner selection.

A reviewed plan binds exact targets, source/target release digest, runtime/native configuration layers, local paths/bytes/modes and managed-block hashes, tool bindings, exceptions, Git state, expected diffs, conflicts, checks and rollback prerequisites. Include shared user-level effects and every enrolled project affected. Show actual diffs before apply. The accepted flow uses the host's native selection/input and approval controls for a consequential target set and actual writes; it adds no Rill approval UI. Local plans are disposable execution/recovery material; GitHub records scope, decisions and summarized outcomes.

Before each write, compare plan inputs again. Changed targets, managed content, exceptions, config, tools or standard invalidate the affected plan. Prepare backups and after-bytes first and write targets serially using existing atomic-write helpers and byte/mode comparisons. Preserve symlinks unless their explicit target is in the approved plan. A lightweight lock/journal may serialize operations and retain before/after state; multi-file and multi-project changes are not atomic.

Preflight every enrolled project before shared runtime/router changes and verify the actual native install, trust and reload sequence. Never auto-trust hooks. A failed or unverified shared change stops dependent project activation. A project failure stops later targets and records completed, failed and pending targets. On interruption, inspect journal and actual state; resume or rollback only through a fresh compatible plan, never blindly retry an unknown outcome.

Drift compares pinned release, expected managed bytes, actual configuration and observed execution. Report Rill-owned block changes separately from valid project bindings/exceptions and unrelated edits. Compare with last applied bytes; a changed managed block is local work to reconcile, not authorization to replace it.

Rollback is a reviewed reverse plan. Restore only when actual bytes/modes still equal the operation's applied after-state; later edits conflict. Reverse only changes owned by the operation. A global runtime rollback considers every current enrollment and availability/trust of the previous runtime. Preserve Git work, credentials, task/outbox evidence and failure records. Reload and verify native behavior: configuration restoration alone does not prove loaded behavior was reversed. Keep applied-but-unverified and rollback-conflict states open.

### Standard contract and project profile

The standard release contains an immutable profile catalog, upstream tool and preset bindings, the Mise tool-lock policy, native package-manager locks, upstream-owned configuration, project roots, exception references, receipt schema, upgrade policy and stack-specific positive/negative fixtures. Each project records the selected profile, committed `mise.lock` resolution/digest, native package-lock digests, upstream config files, actual local command argv, repository-relative working directories, applicable roots and receipt references. Profiles come from repository evidence, not a repository name. Rill owns profile resolution, tool/version pinning, configuration assembly/preservation and execution receipts only. It does not author replacement lint rules, test frameworks, scanners, report evaluators or a quality runner. A rule is an upstream rule with its upstream ID and documented behavior; Rill may bind its ID to a profile and severity only through that tool's native config. Existing Just/package commands remain the executable graph, and hosted jobs call those commands/upstream CLIs directly. Rill records exact argv, exit, duration and report references without changing a tool's result.

### Tool version resolution and locks

Keep the project's Rill standard release pin separate from executable tool versions. Each project continues to pin an immutable Rill standard SemVer and artifact digest through the existing project contract/runtime compatibility map. The standard defines supported tool names and profiles; it does not silently follow a newer standard release. For standalone tool CLIs, declare `latest` in `mise.toml` to select the latest stable release and commit the exact resolved versions/digests in `mise.lock`. The initial lock is created with `mise lock`; local setup and CI reproduce it with `mise install --locked`. An intentional tool refresh uses `mise lock --bump`, reviewed as a dependency/config change with affected positive/negative fixtures and receipts. The committed `mise.lock`, not the word `latest`, is the reproducible execution input.

Keep native dependency locks such as `pnpm-lock.yaml`, `uv.lock`/Python lockfiles and framework package locks. Mise resolves standalone tools; the native package manager resolves project dependencies/plugins. Never replace, regenerate or bypass a package lock as a side effect of Mise setup. Record both lock digests in receipts, and invalidate affected evidence when either changes. ### Exceptions, update policy, and evidence

An exception is not a disabled rule. It binds stable gate/rule ID, exact finding or capability, bounded files, reason, accountable owner, compensating command, decision source, introduced revision and proof it is narrow. Default review is at the earlier of 90 days or the next standard release; a specific shorter date may be chosen for higher-risk debt. No wildcard, directory-wide scanner suppression or silent unknown ID. Credentials, private service entitlement, unavailable runner, unsupported stack, network failure and license ambiguity each have distinct states and costs; none is a green result. Repository owner controls hosted permissions and required checks. No paid entitlement is assumed: CodeQL stays conditional until actual access/cost is verified.

Every gate result binds project root, standard version/digest, profile/config/lock/tool digests, revision/worktree, environment, argv/cwd, exit/signal, duration, output/report hashes and uncovered scope. Redact secret output. PR workflow publishes check outcome and job link; local receipt remains reproducible. Code, lock, rules/config, roots, suppression, runtime, workflow or merge-base change invalidates affected evidence. Re-run affected gates; use full-spec when impact is uncertain. Receipt verification does not rerun a command or prove uncovered human/native acceptance.

Rill standard upgrades remain opt-in reviewed SemVer releases, never automatic. Tool refreshes resolve stable latest only when an owner-approved `mise lock --bump` is run; local and CI install the committed resolution using `mise install --locked`. Release notes enumerate new/removed rules, severity, profile/tool lock changes, coverage, migrations and exception changes. Major or rule-ID removal requires project migration. Dry-run profile/inventory, preserve local state, update exact pin and lock/config, run baseline and negatives, verify project and PR checks, retain rollback to last compatible release. A partial failure stops later writes; rollback compares prior/current bytes and refuses to overwrite edits. This design authorizes no production rollout, trust, publication or project enrollment.

A `run` operation invokes only the exact declared project-native command/upstream CLI argv. Rill never derives “no finding worsened” from raw tool reports; if no upstream-native debt mechanism exists, readiness stays blocked until debt is cleared. Removing the exact debt transitions it to clean. An applicable unavailable host/runner leaves state `external-pending`; it cannot become ready by a document-only declaration.

### Owner-authorized implementation plan: route A

**Goal:** Deliver the first executable upstream quality profile on an independent branch from `main`, with reproducible Mise tool versions, explicit Biome rules/coverage, and native Trivy secret scanning.

**Architecture:** Rill stores upstream tool configuration and receipts only. Mise resolves stable `latest` requests into `mise.lock`; native package managers keep their own locks. Biome and Trivy remain the scanners, with their own rule IDs, file selection, exit codes, and reports. No custom runner, scanner, rule, test harness, or result evaluator is introduced.

**Tech stack:** Mise, Biome, Trivy, existing shell/Git, and native package-manager locks only where selected tools require them.

**Spec:** This #19 proposal, especially the version-resolution section, the profile matrix, native CLI/MCP contract, and new-project acceptance row.

**Global constraints:** Implement on a fresh `main`-based feature worktree. Do not edit the #18 worktree or bring its WIP into the branch. Preserve the current review worktree and `QUALITY-DESIGN.html`. Do not publish, merge, release, or add paid services. Keep exact observed tool versions as evidence, not profile pins. Do not mutate native dependency locks through Mise.

**Review focus:**

- A `latest` request must execute the committed `mise.lock` resolution in local and CI setup.
- A missing, stale, or platform-incomplete tool lock must fail setup, not fetch an unrecorded version.
- Biome's rules and tracked-file coverage must be visible in native config and its effective-config inspection.
- A clean Trivy scan exits zero; a disposable synthetic-secret fixture exits one without storing a real credential or weakening the normal scan.
- Changes to tool locks and project dependency locks remain separately reviewable and invalidate their respective receipts.

**Files:** Create an isolated worktree and feature branch from the current `main`; do not copy from the review worktree or #18. The current `main` snapshot contains only `README.md`, `LICENSE`, and `.gitignore`; reuse only those committed files unless history inspection demonstrates a specific required committed substrate.

- [ ] Verify the review worktree and #18 worktree remain unchanged.
- [ ] Record any selectively extracted committed interface and add a behavior/contract check before using it; no extraction is needed when the main snapshot has no matching interface.

#### Task 2: Add Mise latest resolution and reproducible lock

**Files:** Create `mise.toml` and generated `mise.lock` in the implementation worktree. Declare only the selected upstream standalone CLIs available through maintained Mise backends. Keep ecosystem packages in their native manifests/locks.

- [ ] First validate the selected tool requests with `mise lock --dry-run`; no setup step may write project files beyond the approved lock/config.
- [ ] Create the initial version/checksum/URL lock with `mise lock`, then install with `mise install --locked`.
- [ ] Inspect `mise.lock` to confirm tool identities, resolved releases, checksums/download URLs, and current platform data.
- [ ] Re-run `mise install --locked`; it must reproduce without resolving a newer version. Demonstrate that a deliberate upgrade uses `mise lock --bump` only, with the diff reviewed before installation.
- [ ] Preserve native package locks and record their separate digests in the execution evidence.

#### Task 3: Configure and verify the upstream Biome profile

**Files:** Create root `biome.json`; no Rill lint implementation or custom rule definitions.

- [ ] Run the selected Biome CLI on a clean positive TypeScript/TSX, Markdown, JSON/YAML, CSS/HTML fixture and capture exit/file coverage.

- [ ] Run a negative debugger/correctness fixture through Biome's stdin or disposable path; require the CLI's native nonzero exit. Confirm the clean positive fixture still passes.
- [ ] Use `biome inspect config` and `biome rage`/supported inspect output to confirm effective rules and globs; do not assume the config's text equals effective behavior.
- [ ] Check Tailwind class sorting with the actual selected upstream Biome rule on positive and reversed-order fixtures. If unsupported or unsuitable, keep it outside the blocker profile until an upstream formatter alternative is approved; never add a homemade rule.

#### Task 4: Verify Trivy's native secret gate

**Files:** No custom scanner, parser, wrapper script, tracked secret fixture, or allowlist that hides findings. Add only upstream Trivy configuration if the native CLI requires a project-specific setting.

- [ ] Run `trivy fs --scanners secret --exit-code 1 --quiet --format json .` on the clean tracked checkout; require exit zero and retain the report/receipt.
- [ ] In a temporary directory outside the checkout, create a documented synthetic credential fixture, run the same CLI and require exit one with the expected upstream rule ID. Never emit/store a real credential.
- [ ] Remove the fixture and rerun the clean scan. An unavailable or stale vulnerability DB is not part of this secret-only gate and cannot be called a vulnerability pass.
- [ ] Verify that the full repository root is scanned, with only explicit tracked/generated/vendor paths excluded through Trivy's native configuration.

#### Task 5: Wire the same upstream commands into hosted PR CI

**Files:** Add a least-privilege workflow that installs the committed Mise lock and invokes the same Biome/Trivy commands directly. No new quality runner.

- [ ] Pin workflow actions to verified immutable upstream revisions; use read-only permissions and no secrets for untrusted PR code.
- [ ] Validate workflow syntax and action references, then verify actual PR job execution and required-check settings when the branch is available. A workflow file is not proof that branch protection requires it.
