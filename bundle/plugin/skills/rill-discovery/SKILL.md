# Rill Discovery

Use this **single native entrypoint** for research and grill flows that can alter product scope. It is the only Rill workflow that calls the bundled Superpowers Brainstorming Skill; other Rill skills delegate here instead of duplicating the interview.

1. Discover the current repository, GitHub Issues, exact product scope and relevant targeted PRD requirement lines. **Do not reopen** decisions previously approved by the owner.
2. Invoke installed `brainstorming` **exactly once per substantive decision**, only when genuinely unresolved product design choices exist. Reuse the result across research and grill; no second brainstorming session for the same accepted decision.
3. Research **primary sources** (official upstream standards and runtime behavior), actual code and deterministic checks. Separate observed facts from assumptions before any solution is adopted.
4. Run a focused grill only on consequential remaining tradeoffs, including risk, security boundaries, cost and failure paths; do not invent independent reviewer outcomes.
5. Reconcile proposed design with Rill's Constitution, supported platform constraints and the current PRD. Owner choices require real native structured controls when consequential.
6. Update the current **PRD.md in place** only after an actual decision, and record rationale/task evidence in native GitHub Issues and PRs. Do not create competing DESIGN.md or ROADMAP.md authorities.
7. Hand accepted implementation to upstream native delivery roles. Do not execute destructive or protected actions without separately authorized permission.

For typo fixes, well-scoped repairs, or already-approved implementation, do not trigger an unnecessary brainstorm/grill. If the upstream Builder Check or visual companion is unavailable, record that gap rather than claiming the tool ran.
